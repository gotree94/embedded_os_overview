## 퀴즈

2. `vTaskDelay(10)`과 `vTaskDelayUntil()`의 차이를 설명하고, 주기적 작업에 어느 쪽이 적합한가?

3. ISR에서 태스크를 깨우기 위해 전역 변수 플래그 대신 Queue를 쓰는 이유는? (FreeRTOS API 관점 2가지)

4. 우선순위 역전(priority inversion)이란? Mutex가 이것을 완화하는 원리는?

5. FreeRTOS 커널의 Flash 사용량(대략)과, 네트워크·파일시스템이 포함되지 않는 이유를 설명하시오.

   (a) 태스크마다 MPU 영역 자동 할당 (b) 기본은 공유 보호 없음, MPU 포트로 확장 가능
   (c) MMU로 격리 (d) 항상 메모리 보호 제공

## 답안

1. 기본 설정에서 모든 Task가 **하나의 보호되지 않는 메모리 공간**을 공유하기 때문. 스택 오버플로가 이웃 태스크의 데이터·힙·커널 구조체를 파괴할 수 있다.

2. `vTaskDelay`는 호출 시점부터 정확히 N tick 대기. 주기 작업에 쓰면 실행 시간이 누적되어 주기가 밀린다. `vTaskDelayUntil`은 **다음 절대 실행 시각 기준**이라 주기가 누적되지 않는다. → 주기적 작업에는 `vTaskDelayUntil`.

3. (1) FreeRTOS 큐는 내부가 이미 스케줄러 임계 구간 보호되어 race condition 방지. (2) `xQueueSendFromISR` 계열 API는 ISR 컨텍스트에 맞춰 설계되어 컨텍스트 스위칭 유도(`portYIELD_FROM_ISR`)까지 처리 가능. 전역 플래그는 volatile 선언만으로는 경합을 완전히 막지 못함.

4. 낮은 우선순위 태스크가 뮤텍스를 쥔 채 대기 중, 중간 우선순위 태스크가 계속 실행되어 높은 우선순위 태스크가 무한 지연되는 현상. Mutex는 **우선순위 상속**으로 뮤텍스 소유자의 우선순위를 임시로 끌어올려 방지.

5. 대략 **4~9KB Flash**. 커널은 스케줄링·통신 수단만 제공하는 '실행기'이므로, 네트워크/파일시스템/암호화는 별도 라이브러리 통합이 필요.

6. (b) — Idle Hook은 tick마다·매우 짧게 실행되어야 한다. 1초 지연은 시스템 전체를 마비시킴.

7. (b) 하나의 태스크 (Arduino-ESP32 프리웨임워크 동작).

8. (b) — 기본은 보호 없음. FreeRTOS-MPU 포트로 확장 가능.
