# 최근 임베디드 분야의 AI 포지션 정리

> 대상 독자: `임베디드OS_강의` 6종(Bare Metal~QNX)을 학습한 사람
> 성격: 2주 과정 이후 보충 — **MCU/AP에서 AI(엣지 AI)의 위치와 OS 선택**
> 기준 시점: 2024~2026년 엣지 AI 동향 종합 (수치·제품 사양은 공식 문서로 재확인)

---

## 1. 왜 지금 임베디드 + AI인가

| 변화 | 임베디드에 미치는 영향 |
|---|---|
| 모델 경량화(양자화·프루닝·경량 아키텍처) | 수백 KB~수 MB 모델이 MCU에서 추론 가능 |
| NPU 내장 MCU 등장 (TOPs급) | CPU만으로 못하던 비전/오디오가 실시간화 |
| 프라이버시·통신비·응답속도 | 클라우드 추론 대신 **온디바이스 추론**이 이득 |
| LLM/파운데이션 모델 소형화 | MCU~MPU에서 tiny LLM·임베딩 추론 시도 확대 |

결과: AI는 "별도의 고성능 게이트웨이 기능"에서 **센서 옆에서 도는 기능**으로 이동 중이며, 이는 OS·아키텍처 설계에도 변화를 요구합니다.

## 2. 용어 지도

| 용어 | 의미 |
|---|---|
| **TinyML** | 수 KB~수백 KB RAM의 MCU에서의 머신러닝 (추론 중심) |
| **Edge AI / Endpoint AI** | 게이트웨이~엔드포인트 기기에서의 AI. TinyML을 포함하는 넓은 개념 |
| **추론(Inference)** | 학습된 모델에 입력을 넣어 결과(분류·회귀·이벤트)를 얻는 것. **학습은 대부분 클라우드** |
| **NPU** | Neural Processing Unit. MAC 연산 병렬화 가속기 (INT8 중심) |
| **양자화(Quantization)** | FP32→INT8 등으로 정밀도를 낮춰 속도·메모리 절감 |
| **Wake-word / KWS** | "아리아" 같은 음성 웨이크워드 인식 |
| **이상 탐지(Anomaly Detection)** | 정상 패턴 학습 후 이탈 감지 (진동·전류·센서 시계열) |
| **EdgeBoost / 센서 퓨전** | 다중 센서를 결합해 입력 특징을 만드는 전처리 단계 |

## 3. 워크로드 유형별 MCU 적합성

| 유형 | 입력 | 대략 규모 | MCU 적합성 | 비고 |
|---|---|---|---|---|
| 웨이크워드/음성 이벤트 | 오디오 프레임 | 수십~수백 KB | ◎ | Always-on 저전력 |
| 이상 탐지 (진동·전류) | 센서 시계열 | 수십 KB | ◎ | 산업 예지보전 대표 |
| 결함 검출 (制造业 비전) | 저해상도 이미지 | 수백 KB~수 MB | ○ | MCU+NPU 또는 소형 AP |
| 센서 퓨전 + 자세 추정 | IMU 등 | 수십 KB | ◎ | 웨어러블·도구 |
| 이미지 분류 (MobileNet급) | 96×96~224×224 | 수 MB | △ | NPU 필수급 |
| 오디오 이벤트 분류 (수십 종) | 오디오 | 수백 KB | ◎ | 가전·안전 모니터링 |
| 텍스트/임베딩 검색, tiny LLM | 토큰 시퀀스 | 수 MB~ | △ | MPU~SoC 영역, MCU는 극단적 경량화만 |

범례: ◎ = Cortex-M급에서 실용, ○ = NPU 동반 시 실용, △ = AP/SoC 권장

## 4. 하드웨어 스펙트럼 (AI 관점)

```
 Cortex-M (FreeRTOS 영역)          Cortex-A / SoC (Linux 영역)
 ────────────────────────────────────────────────────────────
 M4/M7        M33/M55/M85+U55/U65      MPU (Cortex-A)      SoC+NPU
 CPU 추론     MCU + NPU 내장/외장       (TFLM 가능)        (고해상도·LLM)
 TinyML       비전·오디오 실시간        비전 파이프라인      온디바이스 LLM
```

대표 칩 계열 (공식 사양 확인 필요):
- **Arm**: Cortex-M55/M85 + **Ethos-U55/U65** — TOPs급 INT8 추론
- **ST**: STM32N6 계열 — 자체 NPU 탑재 라인
- **Espressif**: ESP32-S3(벡터 확장), ESP32-P4(고해상도 애플리케이션)
- **NXP**: MCX N 계열(통합 NPU), i.MX RT 시리즈
- **Renesas**: RA/RZ 계열 + DRP-AI 가속기
- **Nordic**: nRF54 계열 + Edge ML 에코시스템

> 설계 팁: **모델 선정 → 필요한 TOPs/메모리 계산 → 칩 선택** 순서가 아니라,
> 칩에 기본 제공하는 NPU·SDK(X-CUBE-AI, ESP-DL, eIQ 등)를 먼저 확인하고
> 그 위에서 모델을 양자화·재학습하는 쪽이 일정·비용 면에서 유리합니다.

## 5. 소프트웨어 스택 지형

| 계층 | 선택지 | 특징 |
|---|---|---|
| 추론 엔진 | **TFLite Micro (TFLM)** | 가장 널리 쓰임, C++, 양자화 지원 |
| | **CMSIS-NN / CMSIS-DSP** | Cortex-M 최적화 커널. TFLM·다른 엔진 백엔드로 활용 |
| | vendor SDK | ST **X-CUBE-AI**, Espressif **ESP-DL**, NXP **eIQ**, Renesas DRP-AI SDK, Nordic ML |
| | microTVM / ONNX 기반 | 모델 포팅 유연성 |
| | ExecuTorch / llama.cpp(MCU급) | 소형 언어·임베딩 모델 실험 영역 |
| 모델 변환 | TensorFlow/Keras → `.tflite` → 양자화 → C 배열 | 표준 워크플로 |
| OS 통합 | FreeRTOS 태스크 / Zephyr 스레드 + ML 관련 서브시스템 / Linux 프로세스 | 아래 §6 |

**양자화 실무 포인트**:
- INT8 양자화가 속도·메모리의 기본값 (FP16은 NPU 지원에 따라)
- PTQ(학습 후 양자화)로 시작, 정확도 부족 시 QAT(양자화 인지 학습)
- 메모리 예산: 모델 weights + 활성화(activation) + 스택. **activation이 종종 병목**

## 6. OS 포지션: AI는 어디에 두는가 (핵심)

### 6.1 원칙

> **AI 추론은 OS에 "포함"되는 기능이 아니라, OS가 스케줄링·격리·전력 관리를 담당하는 저~중우선순위 워크로드(태스크/프로세스)다.**

- FreeRTOS 커널에 AI 기능이 들어가는 것이 아니라 → **추론 라이브러리를 앱에 링크하고 태스크로 래핑**
- 결정적 제어(제동·안정화·보호 인터럽트)와 추론은 **우선순위·메모리·장애 격리** 측면에서 분리

### 6.2 OS별 포지션 표

| OS | AI 워크로드 위치 | 언제 선택 |
|---|---|---|
| **Bare Metal** | 슈퍼루프 안에서 주기적 호출. 소형 모델·단일 워크로드 한정 | 웨이크워드 수준, 전력 극한, 태스크 1~2개 |
| **FreeRTOS** | **추론 태스크(중·저우선순위)** + 제어 태스크(고우선순위) 구조. 벤더 AI SDK가 FreeRTOS 통합을 1순위 지원 | 지금 가장 실무적인 기본값. "제어 + 가끔 추론" |
| **Zephyr** | ML 관련 서브시스템·센서 파이프라인과 통합. BLE/Matter와 동시 요구 시, Nordic 등 공식 ML 에코시스템 활용 | 연결 스택+AI 표준화, 다중 보드 이식 |
| **VxWorks / QNX** | AI는 User 애플리케이션이나 격리된 프로세스/도메인. 안전 인증이 걸린 시스템에서 ML 허용영역 분리 | 차량(ADAS 인지 파트), 의료·철도 등 인증 환경 |
| **Embedded Linux** | 프로세스 단위 추론(TFLM/PyTorch/ONNX Runtime), NPU 드라이버·프레임워크(Vulkan/NNAPI/NPU SDK) 활용 | 비전·음성·LLM급, 모델 수 MB~GB |

### 6.3 하이브리드 (실제 제품의 다수)

```
[ AP: Embedded Linux ]                    [ MCU: FreeRTOS/Zephyr ]
  · 고해상도 비전 / 음성 LLM급 추론         · 센서 100Hz~kHz 수집 (DMA)
  · 결과 융합·UI·OTA·로그                   · 결정적 제어 루프 (ms 이하)
  · 모델 서빙·동기화                        · 소형 추론(이상탐지·예비판정)
        ↕ UART/CAN/이더넷 (결과·근거값 전달)
```

- Linux가 무거운 추론을 하고, MCU는 **"1차 판정 + 안전 관리"**를 맡는 구조
- 통신 단절 시에도 MCU 쪽 소형 모델로 최소 동작 유지(점검 모드)

### 6.4 태스크 배치 레시피 (FreeRTOS 기준)

| 태스크 | 우선순위 | 주기/방식 | 메모 |
|---|---|---|---|
| 센서 수집 | 상 | DMA+인터럽트, kHz급 | ISR은 짧게, 버퍼만 넘김 |
| 제어 루프 | 상 | 고정 주기 (vTaskDelayUntil) | AI 결과는 참조만 |
| **추론** | 중~하 | 이벤트/주기 (수십~수백 ms) | 청크 분할 가능, NPU 사용 시 드라이버 큐 |
| 결과 집행·로깅 | 하~중 | 추론 완료 이벤트 | MQTT/저장소 |
| OTA(모델 교체) | 하 | 유휴 시간 | 정적 할당·A/B 슬롯 |

원칙:
1. 추론 태스크는 **제어보다 낮은 우선순위**, 절대 ISR에서 금지
2. 추론 중에도 제어 인터럽트가 밀리지 않도록 NPU/DMA 활용
3. 모델 실패(손상·타임아웃) 시 **안전 등급 상태로 복귀**하는 폴백 경로를 설계에 명시
4. 스택은 NN 라이브러리 요구 기준으로 넉넉히 → `uxTaskGetStackHighWaterMark`로 검증 후 감축

## 7. 실시간성·전력·OTA 관점

| 이슈 | 대응 |
|---|---|
| 추론 지연 (soft RT) | 제어(hard RT)와 분리. 프레임 단위 deadline을 애플리케이션에서 관리 |
| 항상 켜짐(Always-on) 저전력 | KWS/이상탐지는 소형 모델+저빈도 추론, 웨이크워드만 상시 |
| 모델 OTA | 모델 파라미터를 펌웨어와 분리해 A/B 슬롯·검증(체크섬·서명) 후 전환 |
| 정확도 드리프트 | 현장 데이터 수집(동의 기반) → 클라우드 재학습 → OTA 순환 |
| 메모리 | 정적 할당 선호, weights 플래시 매핑, activation 예산 별도 검토 |
| 인증·규제 | 의료(FDA/MDR), 자동차(ISO 26262 + AI 안전 가이드라인, UL 4600 등) — **ML 파라미터 변경도 변경 관리 대상** |

## 8. 최근 동향 요약 (2024~2026)

1. **MCU NPU 표준화**: TOPs급 NPU가 중가 MCU까지 확산 → "AI 가능 여부"가 칩 선정 기준의 하나가 됨
2. **벤더 SDK 통합 심화**: X-CUBE-AI/ESP-DL/eIQ 등이 FreeRTOS 프로젝트에 원터치 통합되는 흐름
3. **Zephyr ML 생태계 성장**: Nordic·Arm 등이 Edge ML 샘플·인증 프로그램 제공
4. **tiny LLM/임베딩 실험**: MPU~SoC에서 온디바이스 임베딩·소형 LM, MCU는 KWS·이상탐지 중심으로 역할 분담
5. **하이브리드 상용화**: 차량 SDV(소프트웨어 정의 차량)에서 QNX/Linux 격리 + ML 파이프라인 구조 확산
6. **AI 안전·인증 논의**: 학습 이후 변경(모델 OTA)의 인증 영향, 데이터·평가 문서화 요구 증가

## 11. 6종 OS 프레임과의 연결 요약

| 기존 강의 요점 | AI 시대의 업데이트 |
|---|---|
| Bare Metal: 루프 멈춤 = 전체 정지 | AI 추론 태스크를 넣는 순간 사실상 RTOS 필요 |
| FreeRTOS: 보호 없음, 스택 직접 설계 | NN 라이브러리 스택·힙 폭증 주의, 폴백 설계 필수 |
| Zephyr: 표준화·프로토콜 스택 내장 | ML 파이프라인·NPU 보드 지원도 내장 흐름 |
| Embedded Linux: 생태계, Soft RT | AI 프레임워크 생태계 최강, 제어는 MCU와 분리 |
| VxWorks: 인증 산출물 | 인증 환경에서 ML 변경관리·근거 문서화 요구 |
| QNX: 결함 격리 | ML 추론을 격리 프로세스/VM으로 두는 구조와 궁합 |

5. tiny LLM과 KWS(웨이크워드)의 하드웨어 위치가 다른 근본 이유는?

### 답안 요지

1. FreeRTOS 커널은 스케줄링·동기화만 제공하며 AI 기능 없음. 올바른 포지션은 **추론 라이브러리를 앱에 링크하고 저~중우선순위 태스크로 래핑**하는 것.
2. 추론 지연이 수십~수백 ms로 비결정적이므로, 하드 RT 제어 루프를 밀리게 하면 안 됨. ISR 금지.
3. 예: (1) Linux=카메라 비전 파이프라인, MCU=IMU 기반 자세 판정·비상정지. (2) Linux=음성 인식·LLM 응답, MCU=웨이크워드·저전력 상시 감지.
4. 모델 파라미터는 펌웨어와 분리되어 수시 변경 가능 → A/B 슬롯·서명 검증·자동 롤백 필수. 인증 제품에서는 모델 변경도 변경 관리·재검증 대상.
5. 모델 크기·연산량 차이. KWS는 수십 KB·상시 저전력 → MCU, tiny LLM은 MB~GB·고처리 → MPU/SoC 영역.
