# 데이터 패스·시스템 설계 심화 — DMA, 버퍼링, 메모리 계층

> 2주 과정(6종 OS) 이후 심화 보충
> 관점: 대량 데이터를 CPU 활용에 방해받지 않고 이동·처리하는 법

## 1. 기본 흐름의 관점

센서 데이터를 AI 추론까지 전달할 때, CPU가 센서 값을 직접 읽어 쓰는 대신, **데이터 이동 자체를 하드웨어(DMA)가 담당**하고 CPU는 그 데이터에 대한 **처리(전처리/추론)**에 집중하도록 설계하는 게 목표입니다.

```
센서 ──(직렬/I2C/SPI/SAI/I2S/CAN)──> DMA ──> 링버퍼 ──(전처리)──> 특질벡터 ──(추론)──> 결과 → 제어
```

핵심: 데이터 복사는 CPU 시간이므로, **복사 횟수를 줄인다 = 실효 CPU 여유를 확보**합니다. 이를 보통 **제로커피(Zero-copy)** 관점에서 접근합니다.

## 2. DMA·버퍼링 패턴

| 패턴 | 동작 | 장점 | 주의점 |
|---|---|---|---|
| **단순 DMA** | 버퍼 1개 전송 완료 → ISR | 구현 단순 | 전송/완료 사이 "빈 공간"이 없어 CPU가 대기/교란 시 누락 위험 |
| **더블 버퍼(Dual buffer)** | A를 채우는 동안 B 처리, 완료되면 토글 | 처리와 수집 동시 | 버퍼 2배 메모리 |
| **순환(Circular) DMA** | 버퍼가 끝에 오면 처음으로 되돌아가 계속 채움 | 상시 스트리밍(음성/IMU)에 최적 | **읽기 인덱스/쓰기 인덱스**를 관리해야 유실·중복 방지 |
| **링버퍼 + Half/Complete ISR** | Half 완료시 전처리 시작, Complete 완료시 다음 블록 처리 | "처리 지연"과 "버퍼 오버런"을 분산 | ISR 로직 짧게 유지, ISR→태스크는 큐로 넘김 |

**중요 규칙**: ISR에서 무거운 전처리/추론을 절대 하지 말고, **태스크에 위임**합니다.

## 3. CPU 부하를 줄이는 테크닉: Zero-copy 관점

"제로커피(Zero-copy)"이란 가능한 한 데이터 복사 없이 포인터만 전달하는 개념입니다.

| 테크닉 | 설명 |
|---|---|
| **포인터 전달** | 버퍼 포인터와 길이만 큐/메시지로 전달. 복사 배열 금지 |
| **슬라이스 처리** | 링버퍼에서 "읽기 가능 구간"만 참조 → 블록 넘길 때 memcpy 최소화 |
| **트랜잭션 교체** | 더블버퍼에서 완성된 블록만 교체, 활성 버퍼는 건드리지 않기 |
| **NPU가 DMA 직접 접근** | STM32N6/Neuton 계열 등은 NPU가 버퍼를 직접 소비하는데, 가용 시 메모리 이동 없이 추론 진입 가능 |

## 4. 메모리 계층과 캐시 일관성

Cortex-M7/M33, Cortex-A 계열에서 DMA는 **CPU 캐시와 독립적**으로 메모리에 직접 접근합니다. 따라서 캐시가 틀어질 수 있습니다.

| 요소 | 설명 | 실무 팁 |
|---|---|---|
| **DTCM/ITCM (TCM)** | 데이터/명령 전용 고속 SRAM | ISR 핸들러, 링버퍼, 뮤텍스 핸들 등 타이밍 크리티컬 데이터에 적합 |
| **SRAM** | 대용량 데이터 공간 | 전처리 임시 버퍼, activation 은행 |
| **플래시(XIP)** | 읽기 전용 모델(weights) | 대형 모델 weights는 플래시 직접 매핑 고려. 읽기 전용이므로 캐시가 유리 |
| **外部 RAM(PSRAM/SDRAM)** | 프레임버퍼/장시간 큐 | 프레임 기반 비전은 여기 배치 |
| **DCACHE invalidate** | CPU가 DMA가 쓴 메모리를 읽기 전, 캐시 라인을 무효화 | "DMA 수신 완료 → 처리 전"에 호출 |
| **DCACHE clean** | CPU가 수정한 버퍼를 DMA가 읽어가려 할 때, 캐시 내용을 메모리에 플러시 | "CPU가 버퍼 채움 → DMA 전송 전"에 호출 |

> 참고: 일부 칩은 MPU로 DMA 접근 가능 영역을 제한하거나, Non-cachable 영역으로 링버퍼를 선언해 캐시 일관성 이슈 자체를 회피합니다.

## 5. 버스 대역폭·콘텐션, DMAMUX 우선순위

"대량 데이터" 문제는 단지 CPU 시간만이 아니라 **버스 경합(Bus contention)**입니다. 버스에 접근권은 1개이므로 DMA와 CPU가 동시에 막히면 양쪽 지연이 늘어납니다.

| 항목 | 설명 |
|---|---|
| **버스 대역폭 계산** | 필요 대역폭 ≈ 샘플당 바이트 × 샘플링 주파수 (e.g. IMU 6축 int16 1kHz → 12KB/s). 비전은 MB/s급 → 한계 체크 필수 |
| **버스 마스터 우선순위** | DMA 채널/DMAMUX에서 우선순위 지정. 제어에 직결(ADC·타이머 트리거 등)된 채널이 높은 우선순위 |
| **버스트 길이** | 길게 한번에 전송하면 오버헤드↓, 버스트가 너무 길면 다른 마스터(CPU) 대기 시간↑ |
| **메모리 뱅크 분리** | 가능하면 버퍼는 SRAM 다른 뱅크, weights는 플래시/캐시 경로로 분리해 경합 완화 |
| **AHB/APB 스플릿** | 느린 주변장치(APB) vs 고속(AHB) 경로를 구분 |

## 6. 실무: 상시 스트리밍(AI 입력) 아키텍처 가이드

음성(KWS)과 6축 IMU 기반 이상탐지가 가장 전형적입니다.

| 경우 | 권장 | 비고 |
|---|---|---|
| **KWS(Mel FFT 전처리)** | 순환 DMA(SAI/I2S) + 링버퍼(320~1024 샘플 블록) | Half ISR에서 Mel 추출 시작, Complete는 다음 블록. 추론 주기와 싱크 |
| **IMU(100~1000Hz)** | 순환 DMA(SPI/I2C, or Timer-triggered + DMA) + 더블버퍼 | 슬라이딩 윈도우(예: 256~512 샘플)로 시계열 특징 생성 |
| **저해상도 비전** | DCMI → DMA → 프레임 버퍼 | 센서마다 인터럽트/버퍼 정책 상이. 리사이즈/노말라이즈는 DMA 완료 후 태스크 |

## 7. NPU·고속 오프로드와의 연계

MCU에 NPU가 있으면 **전처리 일부도 하드웨어**로 빼는 게 유리합니다.

| 하드웨어 | 역할 |
|---|---|
| **DMA2D** | STM32 시리즈의 2D 그래픽 가속(이미지 리사이즈/색변환) — 비전 전처리에 유용 |
| **JPEG/ISP 하드웨어** | 압축해제·바이너리화 비용 절감 |
| **NPU 전용 DMA** | NPU가 데이터를 직접 버퍼에서 취득 → 메모리 복사 경로 최소화 |
| **CMSIS-DSP + SIMD** | 전처리(FFT, 필터, 정규화)를 CPU의 벡터 유닛으로 가속. DMA와 병행 최적 |

## 8. RTOS 관점에서의 설계

DMA가 유효한 이유는 **태스크가 대기할 시간을 생산적 처리에 쓰기 위함**입니다. 앞서 대화한 태스크 배치와 합쳐야 제맛이 납니다.

| 항목 | 권장 방식 |
|---|---|
| **ISR은 최소화** | DMA Half/Complete ISR은 "플래그·세마포어·큐 푸시"만 |
| **블로킹 설계** | 전처리/추론 태스크는 큐에서 블록 대기 → 유휴시간 절감, CPU sleep 가능 |
| **우선순위** | 센서 ISR < 제어 태스크 < 전처리 태스크? 구조상 **제어가 제일 높아야**. 추론은 중~하(§6.4 참조) |
| **링버퍼 오버런 체크** | `읽기 인덱스 + 여유 > 쓰기 인덱스` 등으로 CPU가 처리를 못 따라가는 순간 감지 |
| **정적 할당** | 링버퍼·더블버퍼를 정적으로 할당 → 힙 단편화 최소, 인증에도 유리 |

## 9. 체크리스트 (MCU AI 도입 시)

| 번호 | 체크 | 비고 |
|---|---|---|
| 1. | **DMA 경로가 있나?** | SPI/I2C/SAI/UART 중 어떤 게 DMA 지원인지 먼저 확인 |
| 2. | **순환 DMA + 인덱스 관리 코드** | half/complete 이벤트를 태스크로 위임 |
| 3. | **캐시 일관성** | Cortex-M7 등 DCACHE 유무 확인. invalidate/clean 호출 지점 정의 |
| 4. | **메모리 배치** | 링버퍼→TCM, weights→플래시, activation→SRAM |
| 5. | **버스 대역폭 검증** | 시뮬/실측으로 버스 경합 시 제어 지연 영향 확인 |
| 6. | **제로커피** | 포인터만 큐에 전달, 블록 교체 시 복사 최소화 |
| 7. | **폴백** | 링버퍼 오버런/데이터 유실 시 "안전 상태 복귀" 경로 |
| 8. | **전력 절감** | 데이터 충분히 모이면 추론, 아니면 CPU sleep → Always-on 최적화 |

## 10. Bare Metal vs RTOS와의 연결

- **Bare Metal(협력형)**: `now - last` 주기 + 논블로킹 ISR로 버티면 가능. 하지만 복잡해질수록 링버퍼 관리+전처리 태스크화 필요 → 자연스레 RTOS 단위
- **RTOS(선점형)**: "추론 태스크 = 느린 작업"을 블로킹 대기하면서도, **고우선순위 제어 태스크는 언제든 선점** → 이게 DMA+태스크 분리 구조가 빛을 발하는 지점
- **QNX/Linux**: 프로세스 단위 격리(6.6)와 더불어, 고속 데이터는 공유메모리+동기화로, 제어만 소켓/IPC로 분리하는 것도 유효

## 11. 요약

**CPU 활용을 방해받지 않고 대량 데이터를 쓰려면 "얼마나 CPU를 idle에 둘 수 있는가"에 달려있습니다.**

- **반드시 DMA**: 직접 읽기는 폴링 오버헤드·버스 점유로 귀결
- **반드시 버퍼링**: 순환+더블버퍼링이 상시 스트리밍의 사실상 표준
- **캐시/버스 인지**: DCACHE invalidate/clean, DMAMUX 우선순위, 버스 대역폭을 계산·검증
- **제로커피 설계**: 복사 축소 → 추론에 투자할 CPU 여유 확보
- **태스크 분리 + 선점**: DMA ISR은 최소, 전처리/추론은 블로킹 태스크

추론이 제어에 미치는 방식(6.5)보다 **데이터가 제어·추론에 도달하는 경로(이 문서)**를 먼저 단단히 설계하는 게, AI를 실제 임베디드에 얹어도 제어가 흔들리지 않는 가장 확실한 실천법입니다.
